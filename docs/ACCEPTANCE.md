# Приёмка собранного MVP

Проверяется реальное приложение: React из nginx → Go API → PostgreSQL и Redis. Это дополняет Go-тесты и Vitest, которые проверяют отдельные правила и интерфейс с имитацией API.

## Воспроизведение

Нужны Docker Compose 2.24.4+ (поддержка `!override`) и Python 3.12+. Все команды — из корня репозитория. Порты приёмки: интерфейс `18001`, API `18082`. Проект **naparnik-acceptance**, его сеть и тома отделены от обычного запуска на `3001`/`8082`.

```bash
python -m venv .venv-acceptance
. .venv-acceptance/bin/activate
python -m pip install -r scripts/requirements-acceptance.txt
python -m playwright install chromium
# В Linux при отсутствии библиотек браузера: python -m playwright install --with-deps chromium

docker compose -p naparnik-acceptance -f docker-compose.yml -f docker/compose.acceptance.yml up -d --build --wait
python scripts/test_mvp_acceptance.py
```

Конфигурация приёмки отключает чтение `.env` сервисом backend, внешние ключи, Telegram и экспорт событий. Используются только синтетические данные и заглушка модели. Сторожа времени отключены для воспроизводимости браузерного сценария; рабочие сроки и автоактивация проверяются Go-тестами с управляемыми часами. Для установленного системного Chromium можно задать `CHROMIUM_PATH=/usr/bin/chromium`.

Нужен свежий стенд: если он уже использовался, очистить **только его тестовые данные** и повторить запуск:

```bash
docker compose -p naparnik-acceptance -f docker-compose.yml -f docker/compose.acceptance.yml down --volumes --remove-orphans
```

## Что проверяет сценарий

1. Полный цикл знаний: стажёр задаёт вопрос, эксперт отвечает и публикует страницу, следующий стажёр получает ответ из неё без нового обращения к человеку. Разделение ролей: у руководителя нет личного дня, эксперт не читает черновик чужого плана.
2. Бадди правит первый план → сохраняет → отправляет руководителю.
3. Руководитель возвращает с замечанием → бадди дорабатывает → повторная отправка → утверждение.
4. Новая редакция действующего плана не меняет задачи до утверждения; завершённый шаг защищён, прогресс сохраняется.
5. Устаревшая версия получает `409`, идентификаторы шагов не дублируются.
6. Редакция на согласовании переживает перезапуск backend; у стажёра отображается история применённых редакций.
7. Диалог плана на ширине 375 px, отсутствие ошибок JavaScript.
8. Сохранность плана и истории после перезапуска PostgreSQL, Redis и backend.
9. `stub_error` → упрощённый режим с черновиком; `MOCK_FAIL=absence` → `503`, черновик остаётся ожидающим.
10. Сервис восстановлен → подтверждение даёт квитанцию; повтор возвращает ту же квитанцию, заявка одна.

Скрипт во время проверки перезапускает и пересоздаёт backend **только проекта naparnik-acceptance**. После сбоя стенд и снимки экрана сохраняются для разбора. После успешного прогона стенд можно очистить командой выше.

Результаты: `.artifacts/acceptance/result.json`, записанные контракты `contracts.json`, снимки экрана. В GitHub Actions job `Docker Compose — все образы` запускает ту же проверку, сохраняет артефакт `mvp-acceptance` и очищает свой стенд.

Внешняя модель и настоящие сервисы не вызываются. Живой прогон LLM — отдельная проверка из `docs/evals`, его старый результат не считается результатом этой приёмки.
