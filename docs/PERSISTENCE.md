# Постоянное хранение и повторные запросы

Backend сохраняет изменяемое состояние в PostgreSQL: заявки с историей решений,
вопросы и ответы, страницы базы (включая черновики), статусы шагов, счётчики номеров,
черновики действий агента и результаты уже выполненных операций.

## Запуск

Из корня репозитория, с Docker Engine/Desktop и Compose v2:

```bash
cp .env.example .env  # только при первом запуске; существующий .env сохраняем
docker compose up --build -d
docker compose ps
```

Интерфейс: `http://localhost:3000`; API и HTML-версия демо: `http://localhost:8080`.
Без ключей работает заглушка модели. PostgreSQL стартует первым; backend ждёт
готовности БД, frontend — готовности backend. Веб-вход через тестовые учётки.

Проверка сохранения:

1. Создай и подтверди заявку в демо; запомни номер.
2. Выполни `docker compose restart backend`.
3. Обнови страницу: заявка и квитанция должны остаться.
4. `docker compose down`, затем `docker compose up -d` также сохраняют данные.

Данные лежат в именованном Docker-томе `pgdata`. **`docker compose down -v`
удаляет этот том вместе со всеми данными**; это команда сброса демо, а не обычной остановки.
Логи: `docker compose logs -f backend`. Остановка без удаления данных: `docker compose down`.
Пароль PostgreSQL в Compose — демонстрационный; БД не публикует порт наружу.

Без Docker задай `DATABASE_URL` доступного PostgreSQL и запусти `cd backend && go run ./cmd/server`.
Если `DATABASE_URL` пуст, используется явно временный режим в памяти (для тестов/демо).
Если адрес задан, ошибка БД останавливает запуск; незаметного перехода в память нет.

## Как записываются изменения

Для объёма текущего прототипа используется таблица `naparnik_state` с одним
версионированным JSONB-документом. Это намеренно простое хранение состояния,
а не нормализованная схема корпоративных сервисов.

Первый запуск создаёт таблицу и загружает начальные данные из `docs/04-mock-data`.
Следующие запуски читают сохранённое состояние и не затирают его фикстурами.
Изменение фикстур само по себе не обновляет уже созданную базу.

Каждое действие выполняется в транзакции:

1. `SELECT ... FOR UPDATE` блокирует строку и читает последнее состояние.
2. На отдельной копии проверяются права, текущий статус и параметры операции.
3. Применяются все изменения, включая номер, историю и результат операции.
4. Новое состояние записывается и фиксируется `COMMIT`.
5. Только после успешной записи обновляется представление в памяти и возвращается успех.

Ошибка проверки или БД отменяет изменения целиком. Сбой сохранения возвращается как
`unavailable`/HTTP 503; черновик остаётся для повтора. Запросы LLM выполняются вне
транзакций БД. Чтение API обновляет представление из PostgreSQL, поэтому изменения
видны второму экземпляру backend. Начальная инициализация тоже защищена от гонки.

## Что происходит при повторе

| Операция | Идентификатор повтора | Поведение |
|---|---|---|
| Подтверждение действия агента | ID черновика + владелец | Возвращается сохранённый результат; новая заявка/вопрос не создаётся |
| Форма «сделай сам», `POST /api/requests` | Пользователь + `Idempotency-Key` | При том же теле — первая квитанция; другое тело с тем же ключом — 422 |
| Ответ эксперта | ID вопроса + адресат | Тот же ответ — существующие вопрос и страница; другой ответ после выполнения — 422 |
| Публикация | ID страницы + автор | Повтор подтверждения — существующая страница; изменение уже опубликованной страницы этим endpoint — 422 |
| Решение по заявке | ID заявки + согласующий | То же решение — текущая заявка без новой истории; противоречащее — 422 |
| Отметка шага | ID стажёра и шага | Статус остаётся `Done` |

Все проверки выполняются внутри транзакции, поэтому работают и при одновременных
запросах, и между двумя процессами. Для подтверждения ключом служит сам ID черновика.
Завершённые черновики не удаляются: результат нужен для ответа после потери соединения.
`GET /api/drafts` возвращает только незавершённые действия текущего пользователя —
их можно восстановить после перезапуска. Этот список доступен через API; автоматическое
восстановление карточек старого чата в интерфейсе пока не реализовано.

Пример формы через API:

```bash
curl http://localhost:8080/api/requests \
  -H 'X-User: intern.sokolov' \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-access-1' \
  -d '{"kind":"access","system":"sys-redash","reason":"Шаг плана"}'
```

Повтори команду: номер будет тем же. Для новой самостоятельной заявки используй
новый ключ (до 128 символов). Ключ обязателен для этого endpoint; при сетевом сбое
повторяют исходный ключ. API-клиенты формируют ключ автоматически и сохраняют его
для повтора при сетевой ошибке или HTTP 5xx; обновление браузера эту локальную карту сбрасывает.

## Проверки

```bash
cd backend
go vet ./...
go test -race ./...
```

Для интеграционных проверок нужен отдельный тестовый PostgreSQL:

```bash
TEST_DATABASE_URL='postgres://user:password@localhost:5432/testdb?sslmode=disable' go test -race ./...
```

Тесты создают отдельную временную схему и удаляют только её. Без `TEST_DATABASE_URL`
PostgreSQL-тесты явно пропускаются. В CI БД поднимается автоматически; эти тесты исполняются.
Проверяются повторный запуск, два экземпляра backend, параллельные повторы подтверждений,
ответов, публикаций и решений, ключи форм, права и отказ записи с последующим повтором.

## Границы реализации

Практика (SC-30…SC-32) хранится в том же состоянии: этапы, версия и одобрение задания, приватные попытки, события и ID черновика вопроса. Текущий формат снимка — версия 2; версия 1 автоматически читается, а следующая запись сохраняет версию 2. Старый backend не сможет записать снимок версии 2 и удалить незнакомые ему данные. При развёртывании обновляйте все экземпляры backend.

Генерация и проверка LLM выполняются вне транзакции. При записи попытки повторно проверяются пользователь, версия, этап и лимит. Повтор использует `Idempotency-Key`; тот же ключ с другим ответом — 422. Дедлайн одобрения считается по рабочим дням пн–пт и демо-дате сервера. Подробный контракт и границы приватности — [spec/06-practice](spec/06-practice.md).

- Сессии SDK модели/история разговора остаются в памяти. После перезапуска разговор
  начинается заново; это не удаляет бизнес-объекты и черновики действий.
- Все записи сериализуются одной строкой БД. Для большой нагрузки нужны отдельные
  таблицы сущностей и операций; текущий вариант рассчитан на прототип одной команды.
- Подтверждение защищает конкретный черновик, а не два разных черновика с одинаковым
  текстом. Новая самостоятельная заявка с новым ключом — новая операция.
- Результаты операций пока сохраняются без автоматической очистки.
- Имитации сервисов меняют данные в той же транзакции. Для реальных внешних API
  понадобятся поддержка идемпотентности на стороне сервиса или transactional outbox.
- Демо-авторизация `X-User` остаётся демонстрационной; постоянное хранение её не заменяет.
