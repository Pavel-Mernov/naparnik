## Действия людей (не инструменты модели)

Отвечает и публикует только человек — модель эти действия не вызывает (BR-30).

| Действие | Кто | Что происходит | Правила |
|---|---|---|---|
| Ответить на вопрос | Адресат вопроса | Ответ сразу виден стажёру; Напарник создаёт черновик страницы «Вопрос-ответ»: заголовок — суть вопроса, папка — по похожим страницам, похожая страница — предложение дополнить | P2, US-10, US-11, BR-31, BR-32 |
| Опубликовать черновик | Автор ответа | Можно поправить заголовок и текст; после «Ок» страница опубликована под его именем и находится поиском | BR-30, BR-02 |
| Оформить заявку самому | Стажёр | Форма имитации сервиса («Заявки» → «Оформить самому»): те же проверки, что у `create_absence_request` и `request_access`; «Отправить» — подтверждение. Источник заявки `self` | BR-42, BR-40, BR-44 |
| Согласовать / отклонить заявку | Согласующий заявки (руководитель) | `pending` → `approved` (отгул) или `granted` (доступ); отказ — `rejected` с кодом причины из `reason_codes` сервиса, «Другое» — с комментарием. Решение пишется в историю заявки и сразу видно стажёру; выданный доступ предлагает отметить шаг плана | status_flow в absence-service и access-service, SC-14, SC-27 |

### Заявка в сервисе (имитация Jira)

Номер (`ABS-…`, `ACC-…`), автор, согласующий, статус, источник (`agent` — «сделаю за тебя», `self` — «сделай сам»), шаг плана (`step_id`), код причины отказа, комментарий согласующего и история событий (`history[]`: когда, кто, что).

## Формат результата

```json
{ "ok": true, "data": { }, "receipt": { "id": "ABS-1042", "status": "pending", "approver": "Андрей Ковалёв" } }
{ "ok": false, "error": { "code": "forbidden | not_found | validation | unavailable", "message": "…", "who_can": "Андрей Ковалёв" } }
```

HTTP-коды в API: `forbidden` → 403, `not_found` → 404, `validation` → 422, `unavailable` → 503.

## Профили сотрудников (US-38)

Карточка — `{ok: true, profile: {...}}`, список — `{ok: true, profiles: [...]}`. Код — `tools/profile.go`, `httpapi/profile.go`.

| Поле | Откуда |
|---|---|
| `id`, `name`, `position`, `department`, `email` | Оргструктура (`team.json`), не правятся |
| `status` | По главной роли: «Стажёр» важнее остальных, затем «Руководитель», «Бадди», «Эксперт» |
| `phone` | Оргструктура; сотрудник может заменить своим — хранится в состоянии |
| `photo` | `null` или `{url, updated_at}`; `url` меняется с каждым новым фото (`?v=…`) |
| `initials` | Две буквы ФИО — заглушка вместо фото |
| `start_date`, `week`, `buddy`, `lead` | Только у стажёра |
| `can_edit` | `true` у своей карточки |

Правила:

- Видят сотрудники своего отдела (рабочие контакты); отсутствующий или чужой сотрудник — одинаковый 404. Без учётки — 401.
- `PATCH /api/profile` принимает только `phone`: российский номер в любом написании (`+7…`, `8…`, 10 цифр) → `+7 900 123-45-67`. Любое другое поле или неверный номер — 422.
- Фото: тело `PUT` — само изображение, JPEG, PNG или WebP до 512 КБ; тип определяется по содержимому, а не по заголовку (SVG, HTML и прочее — 422). Отдаётся с `Content-Type` формата, `X-Content-Type-Options: nosniff`, `Cache-Control: private`.
- Правка пишет событие `profile_updated` с полем (`phone`, `photo`, `photo_deleted`) без значений. Правки и фото сохраняются в снимке состояния (PostgreSQL) и переживают перезапуск.
- Контакты не передаются модели: инструменты агента (`team_directory`, `get_plan`, `find_expert` …) их не возвращают (BR-72).

Тесты: `TestInternProfile`, `TestProfilePhone`, `TestProfilePhoto`, `TestContactsNotSentToModel`, `TestProfileAPI`, `TestProfileSnapshot`.

## Черновик плана (SC-20, BR-81)

Состояние плана — в `store` (`plans`, сохраняется в снимке PostgreSQL): `draft` → `approved` или `auto_activated`.

- Черновик собирается из шаблона: срок шага — `due_offset` рабочих дней от `start_date` стажёра.
- Стажёр плана не видит, пока он не активирован: `get_plan` → «План ещё готовится: черновик у бадди, утвердит руководитель».
- Правит только бадди стажёра и только черновик: срок — рабочий день `ГГГГ-ММ-ДД`, `removed` убирает шаг, `comment` — руководителю. Руководитель получает «план ждёт утверждения».
- Утверждает только руководитель стажёра: шаги (кроме убранных) становятся задачами трекера, стажёр и бадди уведомлены. Повтор — `validation`.
- Без решения 2 рабочих дня руководителя с `created_at` → `auto_activated`: шаги по шаблону, `get_plan` возвращает `approval: «не утверждён…»`, руководителю напоминание. Утверждение позже снимает пометку.

Тесты: `TestPlanDraftEditApprove`, `TestPlanAutoActivation`, `TestPlanDraftAPI`, `TestPlanStateSnapshot`.

### Редактирование и отмена черновика (BR-14, BR-43, SC-05)

Авторизация — `X-User`. Черновик читает, правит, отменяет и подтверждает только владелец. Для чужого и отсутствующего ID одинаковый 404; без учётки — 401.

| Метод | Путь | Тело / результат |
|---|---|---|
| GET | `/api/drafts` | Только ожидающие черновики владельца |
| GET | `/api/drafts/{id}` | `{ok: true, draft: {id, tool, args, version, status, result?}}` |
| PATCH | `/api/drafts/{id}` | `{version, text?, urgent?}` — правка вопроса, ответ с актуальным `draft` |
| DELETE | `/api/drafts/{id}` | `{version}` — сохранённая отмена любого ещё не выполненного действия, ответ с актуальным `draft` |
| POST | `/api/drafts/{id}/confirm` | `{version}` — выполнить именно просмотренную версию; прежние маршруты подтверждения используют ту же проверку |

`status`: `pending`, `confirmed` или `cancelled`; у отправленного `result` содержит прежний результат с квитанцией. Исходная версия — 1. Правка меняет только текст и срочность `send_question`, увеличивает версию при изменении. Заголовок пересчитывается по тексту; инструмент, владелец и адресат не меняются. Текст — 1…8000 символов после удаления крайних пробелов, без чувствительных ПДн. Права и адресат проверяются повторно до сохранения и перед отправкой. Неизвестные поля и некорректные значения — 422.

Устаревшая версия, правка отправленного/отменённого или подтверждение отменённого — 409. Повтор успешного подтверждения той же версии возвращает прежнюю квитанцию без нового действия. Повтор отмены возвращает прежнюю отмену без новых событий. Ошибка БД — 503 без частичного изменения. Проверка версии, действие и запись выполняются одной транзакцией PostgreSQL, включая запросы с разных экземпляров backend.

Для прежних клиентов подтверждение без `version` допускается только для исходной версии 1. Изменённый вопрос без версии не отправляется. React после ошибки перечитывает серверное состояние; после перезагрузки чата восстанавливает ожидающие черновики. Сохранение правок не отправляет вопрос: требуется отдельное «Подтвердить».

### Оценки ответов и записи встреч (BR-02, BR-36, BR-40)

- `POST /api/feedback`: `{page_id, value: "helped" | "not_helped" | "stale"}`. Оценить можно только опубликованную страницу своего доступного пространства — ту же, которую возвращают база и поиск. Проверка прав и событие выполняются одной транзакцией. Для отсутствующей, закрытой или неопубликованной страницы одинаковый HTTP 404; событие и уведомление не создаются. Некорректный запрос — 422, без учётки — 401.
- `GET /api/meetings` возвращает встречи только их участникам, включая `recording_url`, когда запись есть. В React ссылка «Открыть запись встречи» находится в карточке вопроса участника. Бадди или руководитель, не участвовавший во встрече, ссылку не получает.
- Черновик статьи, опубликованная статья, ответ на вопрос и поиск содержат выжимку с таймкодами без URL записи. Правило применяется и к данным, сохранённым прежней версией backend. Проверку доступа к самой записи выполняет ВКС; в демо используется синтетический URL.

## Нет доступа к системе (SC-33)

`get_access_rules` и `GET /api/services/access/rules?system=…` возвращают `{ok: true, data: {...}}`. Только для стажёра; без учётки HTTP 401, другая роль — 403. Действие только читает каталог: заявок и черновиков не создаёт.

В `data`: текущая `week`, `approver` (`id`, `name`), `systems[]` (`system`, `title`, `status`, `week_from`, `now`, необязательный `step` с `id` и `title` из собственного плана), `self_service_in_app` и `label` с пометкой тестовой инструкции. Системы будущих недель видны, если их разрешено запрашивать. `now` означает срок по плану, а не наличие выданного доступа; фактическое состояние — `status`.

Системы чужого отдела, запрещённые стажёру или без недели выдачи не передаются модели. При прямом запросе такой системы возвращается общий отказ без её названия и описания; закрытые страницы базы для объяснения не читаются. Названия разрешённых систем берутся из каталога сервиса доступов.

Пример: на первой неделе запрос про витрины DWH объясняет, что доступ только на чтение положен со второй недели, связан с собственным шагом `s-10` и согласуется Андреем Ковалёвым. Можно оформить самому через существующую форму или поручить Напарнику. Ранняя заявка допустима: окончательное решение принимает согласующий. Выбор «сделаю за тебя» создаёт обычный черновик `request_access`; отправка — только после подтверждения. Текущий `pending`/`granted` сообщается без предложения повторной заявки.

## Обзор команды (SC-21)

`GET /api/dashboard/team` возвращает `{ok: true, data: {...}}`. Требуется `X-User` с ролью `lead`: без учётки — 401, другие роли — 403. Это HTTP-агрегация для интерфейса, а не инструмент модели.

Поля `data`:

- `department` — название отдела.
- `interns[]` — только пользователи с ролью `intern` и `lead_id` текущего руководителя: `id`, `name`, `buddy`, `week`, `plan_status` (`approved`, `draft`, `missing`), `stage` (название первого незавершённого этапа), `progress_pct`, `overdue_steps`, `open_questions`.
- `requests[]` — только заявки этих стажёров, где текущий руководитель — согласующий: `id`, `kind`, `title`, `type?`, `date?`, `employee_id`, `employee_name`, `status`. Тексты комментариев и причины отсутствия не передаются.
- `totals` — `interns`, `overdue_steps`, `open_questions`, `pending_requests`. Открытые вопросы — статус `Sent`, ожидающие заявки — `pending`. Прогресс и просрочки считаются по шагам с владельцем `intern`.

Тексты вопросов, ответы и маршрут вопросов в этот ответ не входят. Без подчинённых возвращаются пустые массивы и нулевые итоги. Для стажёра без утверждённого плана сохраняется статус черновика; отсутствие плана не показывается как завершённая адаптация.

React использует обзор как стартовый экран руководителя. `/api/today` загружается только для стажёра; бадди явно выбирает план своего стажёра. При смене учётки очищаются старые данные, диалоги и чат, запросы отменяются; перед применением каждого ответа дополнительно проверяется поколение учётки, включая переключение A → B → A.

## Сохранение и повторы

Практика, попытки и приватность: [06-practice](06-practice.md).

Изменяющие действия выполняются транзакционно. Подтверждение черновика повторно возвращает сохранённую квитанцию; ответ эксперта, публикация и решение руководителя защищены проверкой состояния в той же транзакции. `POST /api/requests` требует `Idempotency-Key`; другой запрос с тем же ключом отклоняется. `GET /api/drafts` возвращает незавершённые действия владельца. Контракты и ограничения: [PERSISTENCE](../PERSISTENCE.md).
