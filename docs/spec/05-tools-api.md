## Действия людей (не инструменты модели)

Отвечает и публикует только человек — модель эти действия не вызывает (BR-30).

| Действие | Кто | Что происходит | Правила |
|---|---|---|---|
| Ответить на вопрос | Адресат вопроса | Ответ сразу виден стажёру; Напарник создаёт черновик страницы «Вопрос-ответ»: заголовок — суть вопроса, папка — по похожим страницам, похожая страница — предложение дополнить | P2, US-10, US-11, BR-31, BR-32 |
| Опубликовать черновик | Автор ответа | Можно поправить заголовок и текст; после «Ок» страница опубликована под его именем и находится поиском | BR-30, BR-02 |
| Оформить заявку самому | Стажёр | Форма имитации сервиса («Заявки» → «Оформить самому»): те же проверки, что у `create_absence_request` и `request_access`; «Отправить» — подтверждение. Источник заявки `self` | BR-42, BR-40, BR-44 |
| Согласовать / отклонить заявку | Согласующий заявки (руководитель) | `pending` → `approved` (отгул) или `granted` (доступ); отказ — `rejected` с кодом причины из `reason_codes` сервиса, «Другое» — с комментарием. Решение пишется в историю заявки и сразу видно стажёру; выданный доступ предлагает отметить шаг плана | status_flow в absence-service и access-service, SC-14, SC-27 |

### Заявка в сервисе (имитация Jira)

Номер (`ABS-…`, `ACC-…`), автор, согласующий, статус, источник (`agent` — «сделаю за тебя», `self` — «сделай сам»), шаг плана (`step_id`), код причины отказа, комментарий согласующего и история событий (`history[]`: когда, кто, что).

## Формат результата

```json
{ "ok": true, "data": { }, "receipt": { "id": "ABS-1042", "status": "pending", "approver": "Андрей Ковалёв" } }
{ "ok": false, "error": { "code": "forbidden | not_found | validation | unavailable", "message": "…", "who_can": "Андрей Ковалёв" } }
```

HTTP-коды в API: `forbidden` → 403, `not_found` → 404, `validation` → 422, `unavailable` → 503.

## Сохранение и повторы

Изменяющие действия выполняются транзакционно. Подтверждение черновика повторно возвращает сохранённую квитанцию; ответ эксперта, публикация и решение руководителя защищены проверкой состояния в той же транзакции. `POST /api/requests` требует `Idempotency-Key`; другой запрос с тем же ключом отклоняется. `GET /api/drafts` возвращает незавершённые действия владельца. Контракты и ограничения: [PERSISTENCE](../PERSISTENCE.md).
