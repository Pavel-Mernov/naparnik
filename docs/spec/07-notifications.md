# 07. События, уведомления, Telegram и сторожа сроков

Код: [`internal/store`](../../backend/internal/store) (`events.go`, `notify_rules.go`, `watch.go`, `plans.go`), [`internal/telegram`](../../backend/internal/telegram). Продуктовые правила — BR-18, BR-20, BR-50…BR-53, BR-73, BR-81, BR-85.

## Журнал событий (BR-73)

Каждое значимое действие пишется `store.Emit(type, actor, object, meta)` в той же транзакции, что и само действие. Тексты вопросов, ответов и причины отсутствия в `meta` не кладутся.

Типы: `question_sent`, `question_answered`, `question_rerouted`, `question_open`, `question_overdue`, `page_published`, `pages_merged`, `request_created`, `request_decided`, `step_done`, `kb_answer`, `answer_feedback`, `meeting_scheduled`, `meeting_no_recording`, `intern_idle`, `plan_edited`, `plan_decided`.

Из журнала считаются метрики (`GET /api/metrics`) и последняя активность стажёра (простой).

## Уведомления

`notificationsFor(event)` превращает событие в уведомления людям; сторожа и планировщик ставят их напрямую через `store.Notify`. Повтор с тем же `id` не создаёт дубль — так напоминания и сигналы приходят один раз.

| Поле | Смысл |
|---|---|
| `type` | `question_sent`, `question_new`, `urgent_question`, `answer_ready`, `answer_published`, `draft_review`, `request_sent`, `approval_needed`, `request_status`, `meeting_scheduled`, `meeting_no_recording`, `enable_recording`, `event_reminder`, `morning_plan`, `question_rerouted`, `question_open`, `open_question`, `pages_merged`, `page_stale`, `sla_expired`, `idle_signal`, `plan_review` |
| `text` | Что именно и что сделать дальше; без содержимого вопроса и ответа (BR-51) |
| `view` | Раздел Напарника, куда ведёт уведомление |
| `tg` | `pending` — ждёт отправки, `sent`, `failed` (осталось в вебе), `skipped` (Telegram не подключён), `web` — только веб |
| `deliver_at` | Не раньше этого момента (рабочие часы, сводка) |

Веб: `GET /api/notifications`, `POST /api/notifications/read`.

## Telegram (BR-50…BR-53)

| Правило | Как |
|---|---|
| Привязка — одноразовым кодом | `POST /api/telegram/link` → код `LINK-…` на 10 минут в Redis и ссылка `t.me/<бот>?start=<код>`. `/start <код>` или сам код в чате бота привязывает чат. `/stop` или `DELETE /api/telegram/link` отвязывает |
| При подключении — без пачки старого | Накопленное, пока чата не было, заново не рассылается: бот одним ответом сообщает число пропущенных за сутки и первую строку последнего. Всё остальное видно в вебе |
| Не забывает людей | Привязка — в состоянии (PostgreSQL) и копией `tg:link:<user>` в Redis без срока (AOF на томе). При старте `Restore` возвращает привязки, которых нет в состоянии, и копирует недостающие в Redis |
| Только факт и ссылка (BR-51) | Текст уведомления + «👉 Открыть Напарник: WEB_URL» |
| Рабочие часы и сводки (BR-20, BR-52) | Вне рабочих часов получателя — отложить до начала дня; новые вопросы эксперту — сводкой в 11:00 и 16:00. Демо (`NOTIFY_IGNORE_HOURS=true`) — сразу |
| Не засыпать чат | Срочное — отдельным сообщением. Несколько несрочных к одному моменту — одним: «🔔 Новых уведомлений: N», первые строки, свежие сверху, не больше 5 |
| Сбой не влияет на веб (BR-53) | Ошибка отправки → `failed`, уведомление в вебе. Ошибки опроса бота пишутся в журнал (без токена) |
| Без токена | Режим `log`: сообщения пишутся в журнал сервера |
| Один отправитель | Отправка под блокировкой `tg:flush` в Redis — несколько экземпляров backend не шлют дважды |
| Только уведомления | Любой другой текст боту → «вопросы и заявки — в Напарнике» со ссылкой |

Журнал бота: входящая команда без кода привязки и первая строка ответа (`telegram: входящее "/start <код>" → Готово…`).

## Планировщик (раз в 15 секунд)

`telegram.Service.Schedule` в одной транзакции:

- **Утренний план** — стажёру с режимом «план на день» в начале рабочего дня: число шагов, первым — просроченный.
- **Напоминания о событиях календаря** — за час и, если включено, за день; «завтра» — только если событие действительно завтра по календарю.
- **Встречи по вопросам** — участникам за час; организатору за 5 минут и в начале — «включи запись» (BR-35).
- **Сторожа сроков** — `store.Watch(now)`, ниже.

Затем `Flush` отправляет готовое.

## Сторожа сроков (`store/watch.go`, `store/plans.go`)

Рабочее время считает `AddWorking(hours, from, d)`: будни, окно «10:00-19:00» человека по МСК, остаток переносится на следующее утро. `WorkingDay(hours)` — длина окна (по умолчанию 8 ч).

### SLA ответа (BR-18, SC-23)

| | |
|---|---|
| Какие вопросы | Статус `Sent` |
| Отсчёт | От последнего события `question_sent` или `question_rerouted` по вопросу — после переадресации срок начинается заново |
| Срок | Обычный — рабочий день адресата; срочный — 2 рабочих часа |
| Истёк | Адресату `sla_expired` (веб + Telegram): «ответь, назначь встречу или „Не ко мне“»; событие `question_overdue` |
| Ещё через срок | Бадди стажёра `sla_expired`: «переадресуй или ответь сам». Если бадди и есть адресат — второго шага нет |
| API | `due_at`, `overdue` в `GET /api/questions` |

Тесты: `TestQuestionSLA`, `TestUrgentSLAIsTwoWorkingHours`, `TestAddWorking`.

### Простой стажёра (BR-85, SC-19)

| | |
|---|---|
| Кого | Стажёров с активным планом (`approved` или `auto_activated`; по черновику — нет) |
| Последняя активность | Позднее из: последнее событие, где стажёр — автор; `last_activity_at` из трекера; иначе дата старта |
| Порог | 2 рабочих дня стажёра |
| Сигнал | Бадди `idle_signal`, только веб (`tg: web`), мягкий текст «напиши пару слов или загляни в план»; событие `intern_idle`. Новая активность — новый отсчёт и новый сигнал |

Тест: `TestIdleSignal`.

### Автоактивация плана (BR-81, SC-20)

Черновик плана без решения 2 рабочих дня руководителя с `created_at` → `auto_activated` с пометкой «не утверждён», руководителю `plan_review` с напоминанием, бадди — что план уже виден стажёру. Подробно — [05, «Черновик плана»](05-tools-api.md#черновик-плана-sc-20-br-81). Тест: `TestPlanAutoActivation`.
