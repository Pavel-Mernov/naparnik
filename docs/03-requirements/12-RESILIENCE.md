# 12. Отказоустойчивость

> Что происходит с Напарником, когда что-то ломается: модель, сервис Авито, Telegram, база данных или сеть у пользователя.
> Правила: BR-43, BR-53, BR-70 ([04-BUSINESS-RULES.md](./04-BUSINESS-RULES.md)). Реализация: [spec/04](../spec/04-agent-behavior.md), [spec/07](../spec/07-notifications.md), [spec/09](../spec/09-adapters.md), [PERSISTENCE.md](../PERSISTENCE.md).

## 1. Что мы называем отказоустойчивостью

Напарник продолжает помогать, когда одна из систем, от которых он зависит, недоступна: стажёр получает ответ или понятное «не получилось, вот что делать», **ни один вопрос и ни одна заявка не теряются**, и ничего не выполняется дважды.

Главная зависимость — внешняя языковая модель. Если связи с ней нет («не ловит»), ошибка или ответ дольше **[30 с]**, Напарник переходит в **упрощённый режим**: тот же вопрос обрабатывают правила через те же инструменты, проверки прав и черновики с подтверждением (BR-70).

**Чего это не значит.** Напарник — веб-приложение. Если интернета нет **у самого пользователя** (ноутбук или телефон не в сети), сервер ему недоступен, и офлайн-режима в MVP нет: интерфейс показывает ошибку и «Повторить», набранный текст не теряется (FE-06).

## 2. Принципы

1. **Сбой одной системы не останавливает остальные.** Нет модели — работают правила; нет Telegram — работает веб; нет коллектора аналитики — работает всё, кроме выгрузки.
2. **Запрос не теряется.** Вопрос, черновик и заявка сохраняются до того, как уходят во внешнюю систему; при сбое пользователь нажимает «Повторить».
3. **Повтор безопасен.** Подтверждение черновика и заявка с одним ключом повтора дают одну и ту же квитанцию, а не вторую заявку (BR-43).
4. **Честно говорим, что случилось.** Пометка «Упрощённый режим», понятная ошибка вместо пустого ответа; закрытое по правам при этом не раскрывается.
5. **Права и границы ИИ не ослабляются в аварийном режиме.** Правила вызывают те же инструменты с теми же проверками (BR-40, BR-46, BR-49, BR-72).

## 3. Что ломается и что видит пользователь

| Что недоступно | Что делает Напарник | Что видит пользователь | Где в коде / как проверить |
|---|---|---|---|
| **Языковая модель** (нет сети до провайдера, ошибка, таймаут) | Вопрос передаётся запасному движку на правилах (`Agent.Backup`) — те же инструменты, права и черновики; если и правила не справились — показывает найденные страницы базы без пересказа и частые действия роли | «Думаю…» → пометка «Упрощённый режим» → ответ, черновик отгула или вопроса человеку, кнопки быстрых действий; «Повторить» | `agent.degraded`, `agent.fallback`; `LLM_MODE=stub_error` / `stub_timeout` / `stub_slow`; SC-26 |
| Модель отвечает медленно | Таймаут `LLM_TIMEOUT_SEC` (30 с), интерфейс не блокируется | Статус «Думаю…», остальные экраны работают | FE-06, BR-70 |
| Слишком много запросов к модели | Лимит `LLM_RATE_PER_MIN` на пользователя (Redis) | Просьба подождать, без потери введённого | README → Redis |
| **Сервис Авито** (отсутствия, доступы) | Черновик заявки сохранён, вызов не выполнен; повтор с тем же `Idempotency-Key` | Понятная ошибка, «Повторить»; квитанция появится один раз | `adapters`, `MOCK_FAIL=absence,access`; SC-15, SC-29 |
| Решение по заявке в сервисе не пришло | Статус подтягивается опросом сервиса | Статус обновляется сам | `ABSENCE_SYNC_SEC` |
| **Telegram** | Уведомление остаётся в центре уведомлений веба; при подключении приходит одно сообщение «накопилось N» вместо пачки | Всё видно в вебе | BR-53, `internal/telegram` |
| **Коллектор аналитики** (Clickstream, Kafka) | Выгрузка пачками с повтором; журнал событий в PostgreSQL остаётся источником правды | Ничего — работа не затронута | `adapters/events.go`, `GET /api/health` |
| **Redis** во время работы | Кэш поиска и подбора эксперта считается промахом — ответ собирается заново | Ответ чуть медленнее | `tools/cache.go` |
| **PostgreSQL** | Изменение отменяется целиком, ответ 503 «Хранилище недоступно»; черновик остаётся для повтора | Ошибка и «Повторить»; ничего не сохранено наполовину | [PERSISTENCE.md](../PERSISTENCE.md) |
| Перезапуск backend | Заявки, квитанции, черновики, история чата и «Мои вопросы» — в PostgreSQL; привязки Telegram — в Redis (AOF) | Всё на месте, кроме контекста разговора у модели | Тесты с двумя экземплярами backend |
| Падение контейнера | Docker поднимает его заново, healthcheck у PostgreSQL и Redis | Короткая пауза | `docker-compose.yml`: `restart: unless-stopped` |
| **Сеть у пользователя** | — (офлайн-режима нет) | Ошибка, «Повторить», ввод не теряется | FE-06 |

## 4. Как показать на демо

1. Запустить с `LLM_MODE=stub_error` (или выключить ключ модели) → стажёр пишет «Нужен отгул на пятницу» → пометка «Упрощённый режим» → черновик отгула → «Подтвердить» → квитанция. Сценарий SC-26.
2. Запустить с `MOCK_FAIL=absence` → подтвердить отгул → ошибка сервиса, черновик сохранён → убрать сбой → «Повторить» → одна квитанция. Сценарии SC-15, SC-29.
3. Перезапустить backend (`docker compose restart backend`) → заявки, черновики и история чата на месте.

## 5. Границы MVP и следующий шаг

| В MVP нет | Почему | Следующий шаг |
|---|---|---|
| Офлайн-режим у пользователя | Корпоративные данные не кэшируем на устройстве; демо — на ноутбуке в сети | Очередь отправки в браузере для черновиков, если пилот покажет потребность |
| Контекст разговора с моделью после перезапуска | Хранится в памяти backend; бизнес-объекты при этом не теряются | Хранить сессию разговора в PostgreSQL |
| Запасная внешняя модель | Хватает правил на частые сценарии | Второй провайдер через тот же интерфейс `llm.Provider` (например, внутренняя модель Авито) |
| Горизонтальное масштабирование под нагрузку | Состояние — одна строка JSONB, рассчитано на прототип одной команды | Отдельные таблицы сущностей ([PERSISTENCE.md](../PERSISTENCE.md)) |
| Redis недоступен при запуске | Запуск с ошибкой, без тихого перехода в память — чтобы не потерять коды привязки и блокировки | Оставляем так |
