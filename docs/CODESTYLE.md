# Код-стайл команды

> Общие правила для всех пятерых: бэкенд (Go), ML/LLM, фронт, данные, документация. Основание для правил — кейс Авито ([00-case](00-case/)), бизнес-правила ([04-BUSINESS-RULES](03-requirements/04-BUSINESS-RULES.md)) и SDD-спецификация ([spec](spec/00-overview.md)).
> Ревьюер проверяет PR по этому файлу. Если правило мешает, сначала меняем файл, потом код.

## 1. Главные принципы

1. **Модель выбирает, код решает (BR-40).** Права, проверки и выполнение действий описываются в Go-коде, промпт их не заменяет. Правило из промпта без проверки в коде за правило не считается.
2. **Лестница доверия (BR-11, BR-43).** Всё, что создаёт заявку или пишет человеку, сначала оформляется черновиком. Выполняется только по кнопке человека. В форме сервиса («сделай сам», BR-42) этой кнопкой служит «Отправить».
3. **Заявляем только то, что сделано.** Кейс штрафует за заявленное, но не сделанное. Добавил сценарий — обнови [STATUS.md](STATUS.md). Убрал — тоже обнови.
4. **Только синтетика.** Никаких реальных людей, ПДн, финансов и регламентов Авито. Тестовые инструкции помечаются `test_instruction: true` и в интерфейсе подписываются «тестовая инструкция, не регламент Авито» (BR-05).
5. **Секреты не попадают в git.** Ключи хранятся только в `.env`. В репозитории лежит `.env.example` без значений. Перед коммитом выполни `git diff --cached | grep -n "sk-"`: вывод должен быть пустым.

## 2. Go (backend/)

| Правило | Как |
|---|---|
| Форматирование | `gofmt` обязателен, CI падает на неотформатированном коде. Импорты: стандартная библиотека → пустая строка → свои пакеты |
| Линт | `go vet ./...` без замечаний |
| Структура | Код в `internal/`: `mockdata` (чтение данных), `store` (состояние), `tools` (инструменты и действия людей), `agent`, `llm`, `httpapi`. HTTP-слой только разбирает запрос и вызывает `tools`, бизнес-логики в нём нет |
| Ошибки действий | `*tools.Error{Code, Message}`, где код — `forbidden`, `not_found`, `validation` или `unavailable`. HTTP-статус выводится из кода (403/404/422/503). `Message` пишется по-русски, обращение к стажёру на «ты» |
| Паника | Не используем. Внешний сбой возвращаем как `unavailable`, черновик при этом сохраняется (SC-15) |
| Состояние | Состояние меняется только через методы `store` под мьютексом (`UpdateRequest`, `UpdateQuestion`, `UpdatePage`). Наружу отдаются копии |
| Пользователь | Пользователь всегда берётся из сессии (`X-User` → `Ctx.User`). Аргументам модели вроде `intern_id` не доверяем без проверки |
| Имена | Экспортируем только то, что нужно другому пакету. Константы статусов совпадают с мок-данными (`pending`, `approved`, `granted`, `rejected`) |
| Комментарии | Пишем по-русски. Объясняем, зачем нужен код, и даём ссылку на правило: `// BR-44: объяснить и предложить запрос тому, у кого есть право` |
| Зависимости | Только при реальной необходимости. Сейчас используются стандартная библиотека и два SDK моделей |

## 3. Тесты

- Каждое правило BR и каждый сценарий SC, которые проверяет код, закрываются тестом. В названии или комментарии теста указываем сценарий: `// SC-04 → SC-12: …`.
- Табличные тесты пишем для отказов: перечисляем случаи `forbidden`, `validation` и `not_found`.
- Тесты не ходят во внешнюю модель: используем заглушку `llm.NewStub` или `httptest`.
- Покрытие должно быть не ниже **80%**, проверка идёт в CI. Отчёт строится через `./scripts/coverage.sh`, пересобираем его перед сдачей.
- Перед пушем запускаем:

```bash
cd backend && gofmt -l . && go vet ./... && go test -count=1 ./...
```

`-count=1` отключает кеш результатов тестов: изменения в `docs/04-mock-data/`
за пределами Go-модуля иначе могут остаться незамеченными.

## 4. Агент и промпты (ML/LLM)

- Системный промпт лежит в `backend/internal/agent/system.md`, а не в коде. Каждая правка промпта сопровождается прогоном сценариев из README на заглушке и на живой модели.
- Инструмент описываем в `tools.All()`: имя `snake_case`, описание по-русски, JSON-схема и роли, которым он доступен. Если инструмент создаёт что-то во внешнем сервисе, ставим `Confirm: true`.
- Новый инструмент сначала описываем в [spec/05-tools-api.md](spec/05-tools-api.md), потом пишем код.
- Модели не отдаём служебные id людей и черновиков для показа пользователю. Ответ из базы знаний всегда сопровождается источником, автором и датой (BR-01, BR-04).
- ПДн и вопросы про оценку или штат отсекаются в `guard.go` до вызова модели (BR-60, BR-61, BR-72).

## 5. Фронт (frontend/src/)

| Правило | Как |
|---|---|
| Структура | Feature-Sliced: `app` (каркас и маршрутизация разделов), `pages` (экраны), `widgets` (чат, профиль, карта команды, практика…), `entities`, `features`, `shared` (API, тема, общие элементы). Точка входа — `src/app/main.tsx` |
| Запросы | Все запросы идут через `api(login, path, init)` из `@/shared/api` (FE-03). Учётка передаётся в заголовке `X-User` |
| Безопасность | Данные выводим только как React-узлы. **Запрещено** `dangerouslySetInnerHTML`; Markdown модели рендерит компонент `Markdown` из `@/widgets/chat` |
| Стиль | TypeScript strict, отступ 2 пробела, двойные кавычки, точки с запятой |
| Цвета | Только токены темы (`theme.t.*`, `@/shared/theme`), светлая и тёмная темы. Статусы — через `StatusTag` |
| Тексты | Русский язык, обращение на «ты», без канцелярита. Кнопки называют действие: «Отправить в сервис», «Согласовать» |
| Мобильная версия | Проверяем на ширине 375 px: без горизонтальной прокрутки, нижняя навигация остаётся видна |
| Тесты | Vitest + Testing Library. Пользовательские сценарии — в `src/app/*.test.tsx` на записанных ответах backend (`src/test/fixtures.json`, `src/test/mockApi.ts`); покрытие считается по всему `src`, порог 80% |

## 6. Мок-данные (docs/04-mock-data/)

- JSON-ключи пишем в `snake_case`, id с префиксом: `u-`, `kb-`, `s-`, `sys-`. Номера заявок в стиле Jira: `ABS-1042`, `ACC-2002`, `ADAPT-103`.
- Мок-данные заменяют реальный сервис Авито, поэтому их поля повторяют формат ответа сервиса (`status_flow`, `reason_codes`, `responses`).
- После правки запускаем `python3 docs/04-mock-data/check_mocks.py`.

## 7. Git

- Ветка `main` всегда должна запускаться: `docker compose up --build` и `go test ./...` проходят.
- Работаем в ветках `feat/…`, `fix/…`, `docs/…` и вливаем через PR после зелёного CI.
- Сообщение коммита пишем по-русски и про результат, а не про процесс. В скобках указываем сценарии: `Согласование заявок руководителем и «сделай сам» (SC-14, SC-27, BR-42)`.
- Не коммитим `.env`, `coverage.out`, бинарники и `.DS_Store`.

## 8. Документация

- Новый сценарий или изменение поведения отражаем в [STATUS.md](STATUS.md), README («Порядок проверки») и при необходимости в [spec](spec/).
- Ссылаемся на id из документации (`BR-42`, `SC-27`, `US-10`), а не пересказываем правило.
